# Lab 2 — Mining Multiple Repositories, Cleaning and Integrating Data

A revision guide to the Lab 2 implementation: what it does, how it works, and how to run it.

## 1. Objective

Lab 1 mined five GitHub repositories individually and, for each one, produced `file_metrics.csv` (current source-file characteristics) and `git_history_metrics.csv` (historical change counts). Lab 2 does **not** mine anything again — it takes those ten Lab-1 CSV files as raw input and:

1. Consolidates the five repositories' data into two cross-repository datasets.
2. Cleans and validates both datasets.
3. Merges them into one combined, analysis-ready dataset.
4. Computes and saves descriptive statistics for all three datasets.

The result is a dataset where a file's **static characteristics** (language, LOC, size) can be studied alongside its **historical activity** (how often it changed) — the basis for things like code-hotspot or churn analysis.

| Question | Dataset |
|---|---|
| What does the file look like? | `source_code_dataset.csv` |
| How active has the file been? | `commit_history_dataset.csv` |
| How do the two relate? | `combined_dataset.csv` |

## 3. How to Run

From the `lab2` directory:

```bash
pip install -r src/requirements.txt
python src/main.py
```

The script is **not interactive** — it takes no arguments and asks no questions. All paths are computed from the script's own location (`Path(__file__).resolve().parent.parent`), so it can be re-run safely regardless of the current working directory, as long as it's invoked as `python src/main.py` (a plain `import prepare_datasets` in `main.py` relies on Python adding `src/` to the path, which only happens when `main.py` itself is the script being run).

### Execution stages

```
[1/3] Preparing datasets   → prepare_datasets()
[2/3] Cleaning and merging → clean_and_merge()
[3/3] Generating statistics → analyze_datasets()
```

Each stage is a plain function call; `main.py` wraps the whole sequence in one `try/except` that catches `FileNotFoundError`, `ValueError`, and `Exception`, prints a short message, and returns normally — it does **not** re-raise or exit with a non-zero status, so a failed run still exits with code 0.

## 4. Module Responsibilities

### `prepare_datasets.py` — consolidation

For each of the five repositories (`flask`, `requests`, `pytest`, `fastapi`, `scikit-learn`, in that fixed order):

- Reads `data/input/<repo>/file_metrics.csv`, keeps only `file_path, language, extension, loc, size_bytes`, and inserts a `repository` column (lower-cased, stripped) at position 0.
- Reads `data/input/<repo>/git_history_metrics.csv`, keeps only `file_path, change_count`, and adds the same `repository` column.
- Raises `FileNotFoundError` if either CSV is missing, or `ValueError` if a required column is missing.

All five repositories' source rows are concatenated into one DataFrame and saved as `output/source_code_dataset.csv`; the five history DataFrames are concatenated and saved as `output/commit_history_dataset.csv`. **No cleaning happens at this stage** — these two files are the raw, concatenated Lab-1 data plus a `repository` tag, nothing more.

### `clean_and_merge.py` — cleaning, validation and join

Reads the two CSVs that `prepare_datasets.py` just wrote (from disk, not from memory) and cleans each independently:

**`clean_source_dataset`**
- Lower-cases/strips column names; drops fully empty rows.
- Strips and fills `repository`, `file_path`, `language`, `extension` as strings.
- Normalizes `file_path` separators (`\` → `/`).
- Coerces `loc` and `size_bytes` to numeric (non-numeric values become `NaN`).
- Drops rows with empty `repository`/`file_path` or non-numeric `loc`/`size_bytes`, and drops rows where `loc` or `size_bytes` is negative.
- Casts `loc`/`size_bytes` to `int`.
- Drops duplicate `(repository, file_path)` pairs, keeping the first.

**`clean_history_dataset`** — same text/path normalization, plus:
- Coerces `change_count` to numeric and drops invalid/negative rows.
- Instead of dropping duplicate `(repository, file_path)` rows outright, it **aggregates them by summing `change_count`** via `groupby` — duplicate history rows for the same file are treated as additional recorded changes, not discarded.

**`merge_datasets`** — joins the two cleaned DataFrames with:

```python
pd.merge(source_df, history_df, on=["repository", "file_path"], how="left")
```

It's a **LEFT JOIN** keyed on the composite key `repository + file_path` (needed because the same relative path, e.g. `src/main.py`, can exist in multiple repositories). The source-code dataset is the left/base side, so every current source file is retained even if it has no matching history row; such rows get `change_count = 0` (via `fillna(0)`) and a derived boolean column `history_present = change_count > 0`. The result is saved as `output/combined_dataset.csv`.

Only `combined_dataset.csv` goes through this cleaning step — `source_code_dataset.csv` and `commit_history_dataset.csv` on disk remain the uncleaned, prepare-stage output (see §7).

### `analyze_datasets.py` — statistics

Re-reads all three CSVs from `output/` (again from disk, independently of the in-memory objects the earlier stages produced) and computes a statistics dictionary for each, saving each as indented JSON via `json.dump(..., indent=4)`.

### `main.py` — orchestrator

Imports and calls `prepare_datasets()`, `clean_and_merge()`, `analyze_datasets()` in order, printing progress banners between each. Contains no data-processing logic of its own.

## 6. Key Concepts

- **Composite join key (`repository + file_path`)**: `file_path` alone isn't unique across repositories — `flask` and `requests` can both have a `src/__init__.py`. Tagging every row with its `repository` before concatenating, and joining on the pair, keeps records from different repositories from colliding.
- **"Combining structured and historical data"**: `source_code_dataset.csv` is a static snapshot (what a file looks like right now); `commit_history_dataset.csv` is a historical signal (how often it changed). `combined_dataset.csv` is the join of the two — the dataset that actually lets you ask "do larger/more complex files change more often?"
- **LEFT JOIN, not INNER JOIN**: using source-code as the base means a file with zero recorded history still appears in the combined dataset (with `change_count = 0`), rather than being silently dropped.
- **Two-stage disk round-trip**: each stage function reads its inputs from the CSVs the previous stage wrote to `output/` and writes its own outputs back to `output/` — data is not passed between stages as in-memory DataFrames. This makes each stage independently re-runnable (e.g. `python src/clean_and_merge.py` alone), as long as the previous stage's output already exists.

## 7. Points to Remember for Revision

- **`source_code_dataset.csv` / `commit_history_dataset.csv` are *not* cleaned.** Only `combined_dataset.csv` goes through `clean_source_dataset` / `clean_history_dataset`. The first two JSON statistics files therefore summarize the raw, concatenated-but-unvalidated data; only `combined_dataset_statistics.json` reflects post-cleaning data. On the actual Lab-1 fixture data in this repo, cleaning happens to remove zero rows (record counts are identical before/after), but the code path is still different — don't assume the three JSON files were built from equivalently-processed inputs.
- **Duplicate handling differs by dataset**: source-code duplicates on `(repository, file_path)` are dropped (`keep="first"`); history duplicates on the same key are **summed**, not dropped.
- **`history_present` is derived, not read from a file** — it's `change_count > 0`, computed after the left join and the `fillna(0)`.
- **Repository order is fixed**: `REPOSITORIES = [flask, requests, pytest, fastapi, scikit-learn]` in `prepare_datasets.py` — this is also the row order in the two prepared CSVs.
- **Failed stages don't fail the process**: `main.py`'s `except` blocks print an error and return normally, so the process exit code is `0` even after a caught error.
- `requirements.txt` lists only `pandas>=2.0.0`, and it's the only third-party import used across all four modules (`pathlib` and `json` are standard library) — unlike Lab 1, there's no unused dependency here.

## 8. Common Issues

- **`[ERROR] Required file not found.`** — one of `data/input/<repo>/file_metrics.csv` or `git_history_metrics.csv` is missing for one of the five fixed repositories; all five must be present.
- **`[ERROR] Invalid dataset structure.`** — a required column (`file_path, language, extension, loc, size_bytes` for source; `file_path, change_count` for history) is missing from an input CSV.
- **Running `clean_and_merge.py` or `analyze_datasets.py` directly without first running `prepare_datasets.py`** — both read `output/*.csv` files that an earlier stage is responsible for creating; running them out of order raises `FileNotFoundError`.
- **Re-running the pipeline overwrites `output/`** — all six generated files are overwritten in place on every run (except `Lab_Submission/`, which the pipeline never touches).
